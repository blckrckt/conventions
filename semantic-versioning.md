# Конвенция использования SemVer

Документ описывает, как версионируются наши проекты по схеме [Semantic Versioning](https://semver.org/).

## Формат

```
MAJOR.MINOR.PATCH
```

Например: `2.4.1`.

- **MAJOR** — несовместимые изменения, ломающие обратную совместимость.
- **MINOR** — новая функциональность, совместимая со старой.
- **PATCH** — исправления багов без новых функций.

При повышении старшего номера младшие обнуляются: `1.4.2` → `2.0.0`.

## Доп. метки

- Пререлизы: `1.0.0-alpha`, `1.0.0-rc.1`.
- Метаданные сборки: `1.0.0+build.5`.
- `0.x.y` — ранняя разработка, API ещё нестабилен.

## Правила на проектах

- Версия повышается при мердже в основную ветку под аппрувом CTO.
- Тип изменения определяется по характеру PR: багфикс → PATCH, новая функция → MINOR, ломающее изменение → MAJOR.
- Релиз помечается git-тегом вида `v2.4.1`.
- Решение о выпуске релиза и проставлении версии принимает CTO (та же контрольная точка, что и деплой).
- До стабилизации API проект остаётся на `0.x.y`; переход на `1.0.0` означает первый стабильный публичный API.
