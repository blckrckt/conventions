# Конвенция деплоя и релизов

Документ описывает, как изменения попадают в продакшн.

## Окружение

Мы используем только одно окружение — продакшн; у нас нет промежуточных окружений, например staging или dev. Как следствие, единственная проверка, которая выполняется перед деплоем на продакшен, — это ревью на этапе pull request’а и тесты, если они есть на проекте. Поэтому дисциплина CI и ревью здесь критична (см. [Конвенция работы с Pull Request](pull-requests.md)).

## Механизм деплоя

Деплой запускается оформлением Release в GitHub с присвоением тега версии вида `v3.135.1`:

1. CTO одобряет изменения, содержащиеся в pull request’е, и мерджит их в `main`;
2. CTO определяет, стоит ли оформлять GitHub Release с тегом по SemVer (см. [Конвенция использования SemVer](semantic-versioning.md)), по накопленным изменениям (мерджам) — это та самая контрольная точка деплоя из [Конвенция работы над задачами в GitHub Projects](github-issues.md);
3. CTO публикует Release, запуская тем самым GitHub Actions, который доставляет код в продакшн.

Тег Release является версией проекта и командой для деплоя — отдельной кнопки «деплой» у нас нет.

## Release notes

В описание Release попадает changelog, собранный из сообщений коммитов (см. [Конвенция Conventional Commits](conventional-commits.md)): `feat` → новые функции, `fix` → исправления, `BREAKING CHANGE` → ломающие изменения.

## Откат

При откате каких-либо изменений, мы все равно увеличиваем версию продукта, а не понижаем ее, потому что откат — это движение вперед к новой исправной версии, а не возврат к старой. Мы не выкатываем прошлый тег поверх нового, а выпускаем новую версию, в которой проблемного изменения уже нет.

### Процесс

Допустим, в продакшене у нас находится версия `v3.135.1`, и в ней неисправна функциональность из pull request’а #210.

1. **Отменяем изменение в ветке `main`.** `git revert` берет коммит (или мердж-коммит pull request’а) и создает новый коммит с обратными правками. История не переписывается — старый коммит остается на месте, поверх ложится «анти-коммит». Для мердж-коммита pull request’а используется флаг первого родителя:

   ```
   git revert -m 1 <хеш мердж-коммита>
   ```

> Мердж-коммит (тот, что создается, когда pull request вливается в ветку `main`) имеет двух родителей: одна линия — это ветка `main` до влития, вторая — ветка с функциональностью, которую вливали. И тут возникает неоднозначность: когда вы говорите «откати этот мердж», git не знает, относительно какой из двух линий считать изменения. Сам он выбрать не может и без подсказки откажется выполнять revert с ошибкой.
>
> Флаг `-m` (от _mainline_) — это и есть подсказка. Вы указываете номер родителя, который нужно считать «основной линией», то есть тем состоянием, к которому мы должны вернуться.
>
> `-m 1` — первый родитель. Для мердж-коммита первый родитель — это всегда та ветка, в которую мерджили, то есть `main`. Поэтому `git revert -m 1` означает «верни ветку `main` к тому виду, в котором она была до этого мерджа, отменив все, что притащила влитая ветка».
>
> Если pull request вливался через squash («Squash and merge»), в `main` попадает обычный одиночный коммит без двух родителей — тогда флаг `-m` не нужен, откат делается простым `git revert <хеш>`.

2. **Проводим revert по обычному пути.** Revert не вписывается в ветку `main` напрямую и не идет в обход правил — он проходит ту же цепочку, что и любая задача: отдельная ветка → PR → ревью CTO → мердж. Содержимое изменения в данном случае — это отмена предыдущего мерджа, но процесс при этом все равно сохраняется обычный.

   **Через командную строку:**

   ```
   # ветка под откат от свежего main
   git checkout main
   git pull
   git checkout -b fix/211-revert-broken-feature

   # сам revert — создает коммит с обратными правками
   git revert -m 1 <хеш мердж-коммита>

   # пушим ветку
   git push -u origin fix/211-revert-broken-feature
   ```

   Затем открываем pull request из этой новой ветки в `main`. В описании по шаблону: что откатываем и почему, и `fixes #211` (заводим issue на инцидент, чтобы откат был привязан к задаче). Ставим CTO ревьюером — карточка идет в `In Review`.

   **Через интерфейс GitHub (быстрее):** на странице смердженного pull request’а есть кнопка **Revert** — она сама создает ветку с revert-коммитом и открывает готовый pull request, без ручной возни с `-m 1` и хешами. Дальше все то же: назначаем CTO ревьюером, он мерджит. Командная строка нужна, только если кнопка не срабатывает (например, конфликты).

   В обоих случаях гейт ревью остается: даже срочный откат не минует апрув CTO и не пушится в `main` мимо pull request’а. Просто в инцидентной ситуации это делается за минуты.

3. **Выпускаем патч-релиз.** Был `v3.135.1` → CTO оформляет Release с тегом `v3.135.2`. Это `fix` по SemVer (см. [Конвенция использования SemVer](semantic-versioning.md)). Публикация Release запускает Actions, и в продакшен деплоится состояние без сломанной функциональности.

### Что это дает

- Прод всегда строго соответствует последнему выпущенному тегу — никакой неоднозначности в вопросе что реально находится на продакшене нет;
- История версий линейная и честная: по тегам видно, что `v3.135.1` откатили в `v3.135.2`;
- Когда функциональность починят, она вернется как новый `feat` (`v3.136.0`) с исправленным кодом.

### Тонкости

- Revert логически отменяет изменения, но номер версии назад не отматывается: двигаемся только вверх (`3.135.1 → 3.135.2`), даже если контент вернулся к состоянию `3.135.0`. Для SemVer это нормально.
- Когда будете до-делывать откаченную фичу, не забудьте «отменить отмену» (revert revert’а) или переписать ее заново — иначе обратный коммит продолжит гасить изменения.

> **Почему так.** Revert не удаляет фичу из истории — он кладет поверх нее «гасящий» коммит с противоположными правками. Оба коммита (и сама фича, и ее отмена) остаются в `main` навсегда; на диске фичи как будто нет, потому что два противоположных изменения взаимно погасились.
>
> Ловушка в том, что гасящий коммит никуда не девается. Если через неделю вы просто **вольете ту же ветку фичи обратно** тем же мерджем, git сравнивает состояния, а не намерения — и с его точки зрения эти изменения уже отменены. В лучшем случае получите пустой или конфликтный мердж, в худшем — фича вроде влилась, но часть ее правок молча отсутствует, потому что revert-коммит их «съел».
>
> Поэтому есть ровно два честных способа вернуть фичу:
>
> - **Отменить отмену** (revert revert’а) — `git revert <хеш revert-коммита>`. Минус на минус дает плюс: исходная фича возвращается как была. Подходит, когда код менять не надо — фичу откатили из-за чужой поломки или преждевременности, а сама она корректна.
> - **Переписать заново** — новая ветка, исправленная версия фичи свежими коммитами. Это новый код, и гасящий revert-коммит на него уже не распространяется, потому что это не «те же самые» изменения, что он отменял. Получится новый `feat` (`v3.136.0`).

## Секреты

Ключи и токены для деплоя хранятся в GitHub Actions Secrets, в репозиторий не коммитятся.
