# Конвенция ветвления (GitHub Flow)

Документ описывает модель ветвления на наших проектах. За основу взят [GitHub Flow](https://docs.github.com/en/get-started/using-github/github-flow). Именование веток следует спецификации [Conventional Branch](https://conventionalbranch.org/) — kebab-case, строчные буквы, номер задачи.

## Модель

- **main** — единственная долгоживущая ветка, из нее всегда может быть осуществлен деплой;
- От `main` создается короткоживущая ветка под задачу;
- Работа оформляется в [pull request](pull-requests.md), проходит ревью другого разработчика и CTO, мержится обратно в `main`.

Долгоживущей ветки `develop` и релизных веток нет — путь всегда прямой: ветка → pull request → `main`.

## Префиксы веток

- **feat/** — новая функциональность;
- **fix/** — исправление бага;
- **hotfix/** — срочная правка;
- **chore/** — рутина (зависимости, конфиги);
- **refactor/** — рефакторинг без смены поведения;
- **docs/** — документация;
- **build/** — сборка и CI.

Магистральная ветка `main` префикс не использует.

## Формат имени

```
тип/номер-задачи-краткое-описание
```

Примеры:

```
feat/42-user-validation
fix/108-login-crash
chore/update-deps
```

## Правила именования

- Номер issue в начале — для явной связи ветки, pull request’а и задачи;
- Описание в kebab-case, только строчные буквы;
- Описание короткое — суть задачи в 2–4 слова.

## Деплой

Деплой не происходит автоматически при слиянии в `main`, а осуществляется по отдельному решению CTO, принимаемому после мерджа и проставления тега версии.

## Связь с задачами

Номер задачи в имени ветки дополняет, но не заменяет ссылку на issue в коммитах и pull request’ах. В описании pull request’а используются ключевые слова `fixes #номер` для автозакрытия задачи.
