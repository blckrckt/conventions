# Конвенция по написанию кода

## Настройка проекта

- Удалять ненужные файлы из базового проекта
- В скрипте `dev` в конце дописать флаг `--open` для избежания ручного перехода по ссылке
- Индентация должна происходить с помощью пробелов, один уровень индентации это 2 пробела (настраивается в vscode)
- В конце каждого файла должна быть пустая строка ([как добавить](https://stackoverflow.com/questions/44704968/visual-studio-code-insert-newline-at-the-end-of-files), [зачем добавлять](https://stackoverflow.com/questions/44704968/visual-studio-code-insert-newline-at-the-end-of-files))
- Для удобства можно добавлять папки вида `(auth)` - например, для группировки страниц `login` и `register`, они не влияют на маршрут и упрощают поиск нужных файлов страниц
- Настроить перенос длинных строк в vscode для читаемости

## Стилистика кода

- Убирать ненужные точки с запятой в конце
- Везде писать одинарные кавычки `''`, двойные нужны в случае, если в строке есть одинарные, например `"I'm happy to code"`
- Для импорта файлов c расширением `.svelte.js` в конце обязательно явно указывать расширение `import { addTask } from './state.svelte.js'`, чтобы не перепутать с файлами компонентов `.svelte`
- Использовать implicit return в стрелочных функциях\
  ```
  const getTasks = () => return tasks - НЕТ
  const getTasks = () => tasks` - ДА
  ```
- Не писать функции ради функций, например нет смысла в отдельной функции `const add = () => count += 1`, если можно написать `count++`, где оно используется
- Добавлять достаточное число пробелов в выражениях

  ```
  const a=b+c - НЕТ
  const a = b + c - ДА
  ```

  То же самое относится и к пропам

  ```
  let {done=$derived(), title}=$props() - НЕТ
  let { done = $derived(), title } = $props() - ДА
  ```

- Если для объяснения кода необходимо писать комментарии, то код непонятный и требует рефакторинга
- Если уровень вложенности больше 2 - необходим рефакторинг ([пример на С++](https://www.youtube.com/watch?v=CFRhGnuXG-4), смотреть идею рефакторинга, а не стилистику кода)
- Наименование булевых переменных лучше начинать с is (`isOddNumber`, `isNodeModule` и тд)
- Наименование функции должно отвечать на вопрос что делает функция, например `addNumber`, `calculateTax`, `displayError`, `formatDate` и тд
- При наименовании переменных необходимо соблюдать последовательность, например, если есть задача со свойством `done`, то для получения невыполненных задач необходимо назвать переменную `undoneTasks`, а не `unfinishedTasks`
- Не использовать сокращенные названия переменных, тк сокращения не всегда понятны `res` это `result` или `response`?
- Для удобства лучше использовать деструктуризацию

  ```
  {#each tasks as {title, done}}
    <p>{title}</p>
    <input type="checkbox" checked={done} />
  {\each}
  ```

  ```
  let { data } = $props()
  let { tasks } = $derived(data.tasks)
  ```

- Избегать дублирование свойств типа `src={src}` и `title: title` вместо `{src}` и `title`
- Блоки (#each, #if и тд) индентируются

  ```
  <div>
    {#each tasks as task}
      <p>{task}</p>
    {/each}
  </div>
  ```

- Если единичное условие if, то нет смысла писать с фигурными скобками в несколько строк `if(statement) return 1`
- Если 2 return и появляется дополнительный уровень вложенности из-за `if`, то решение либо тернарный оператор, либо охранное выражение
- Обработка ошибок (try / catch)
- При получении ответа проверять условие `!response.ok`

  ```
  export async function load({ fetch, params }) {
    const { id } = params
    const response = await fetch(`https://jsonplaceholder.typicode.com/users/${id}`)
    if (!response.ok) throw error(response.status)
    const post = await response.json().catch(handleJSONError)
    return { post }
  }

  export const handleJSONError = (error) => { console.warn('Проблема с парсингом' )}
  ```

## Стили

- Для задания стилей использовать классы, не теги
- Наименование классов в соответствии с [БЭМ](https://bem.info/ru/methodology/quick-start/)
- Все свойства пишутся в алфавитном порядке, это нужно для быстрой ориентации в коде

  Пример

  ```
  .block{
    align-items: center;
    background-color: red;
    color: green;
    display: flex;
    font-size: 12px;
  }
  ```

- Размеры единиц только пиксели
- Не использовать !important, это нарушает специфичность
- Для задания цвета лучше писать свойство `background-color`, а не `background`
- Не использовать `margin` для задания отступов, для этого есть `flex`, `grid`
- На интерактивные элементы (кнопки, чекбоксы и тд) для лучшего UX надо добавлять свойство `cursor: pointer`
- Не использовать код из dev режима в фигме, за исключением сложных градиентов
- Проверять верстку на различных браузерах (Для проверки на винде браузера Safari используй [Browserling](https://www.browserling.com/) или [BrowserStack](https://www.browserstack.com))
- Если при изменении значений (например, увеличение счетчика) в браузере верстка начинает ехать, необходимо это исправить
- При создании меню с навигацией необходимо блокировать переход ссылки на саму себя (одно из решений - рендерить `<span>` вместо `<a>`, или через стили `pointer-events: none`)
