# Конвенция работы с Pull Request

Документ описывает, как мы оформляем и ревьюим пул-реквесты.

## Оформление PR

- Один PR = одна задача;
- В описании PR обязательна ссылка на задачу через ключевое слово: `fixes #номер` (отдельной строкой внизу);
- Описание короткое и понятное: что сделано, как проверить.

Шаблон описания:

```markdown
## Что сделано

Краткое описание изменений.

## Как проверить

1. Шаг
2. Шаг

fixes #1
```

## Ревью

- Перед подачей PR на ревью необходимо решить все мердж конфликты;
- Все PR проходят минимум два одобряющих ревью перед мерджем — **включая PR от CTO**;
- Ревьюерами PR разработчиков выступает сначала другой разработчик, потом CTO;
- PR самого CTO ревьюят два джуна (формальный ревью);
- **ВАЖНО!!!** Если задача имеет статус `Critical`, и нет возможности получить ревью от другого разработчика - СРАЗУ кидать CTO на ревью.

### Зачем ревьюить PR от CTO

- Учебный эффект: джуны читают код более опытного человека, видят подход к решению, структуре, тестам;
- Лишний взгляд ловит мелочи: опечатки, забытые файлы, отладочный мусор;
- Культура: ревью — норма для всех, а не повинность джунов.

### Правила здорового ревью

- Approve означает «прочитал, понял замысел, вопросов нет», а не «гарантирую корректность»;
- Вопросы «почему так?» приветствуются — это и есть обучение;
- Request changes на PR от CTO — это нормально и поощряется, а не дерзость;
- Автор делает PR небольшими и с понятным описанием, чтобы ревью был посилен;
- Если комментарий от ревьюера не содержит в себе прямого вопроса и не требует пояснений со стороны автора пра, то после исправления его можно резолвить.

## Важный технический нюанс

GitHub не позволяет автору одобрить собственный PR. Поэтому при включенном требовании «минимум 1 апрув» PR от CTO не сможет быть смержен без ревью джуна — что и закрепляет практику формального ревью.
