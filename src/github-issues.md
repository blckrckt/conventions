# Конвенция работы над задачами в GitHub Projects

Документ описывает, как команда ведет задачи в GitHub Projects: движение карточек по доске, контрольные точки и правила работы с pull request’ами.

## Роли

- **CTO** — единственная точка контроля: код-ревью, решение о закрытии задач и деплой;
- **Разработчики** — берут задачи, пишут код, открывают pull request.

## Колонки (поле Status)

`Todo` → `In Progress` → `In Review` → `Done`

- **Todo** — готовы к взятию, назначен исполнитель;
- **In Progress** — кто-то активно работает над задачей;
- **In Review** — все, что сюда попало, ждет ревью;
- **Done** — pull request получил два аппрува и смержен CTO.

Деплой не отражается отдельной колонкой — это отдельное решение CTO, которое принимается после `Done`.

## Движение задачи

1. Создается issue, кладется в `Todo`, назначается исполнитель (assignee);
2. Разработчик берет задачу → переводит в `In Progress`, создает ветку;
3. Открывает PR с `fixes #42` в описании, ставит другого разработчика ревьюером → карточка идет в `In Review`;
4. Другой разработчик делает ревью. Если есть правки — комментарии, разработчик дорабатывает, карточка идет в `In Progress`;
5. После аппрува от разработчика ставит СТО ревьюером. Если есть правки — комментарии, разработчик дорабатывает, карточка идет в `In Progress`;
6. CTO аппрувит и мержит PR → issue закрывается автоматически (из-за `fixes`), карточка уходит в `Done`;
7. После мерджа нужно удалить ветку - она больше не нужна.
8. Деплой выполняет CTO отдельным решением после закрытия задачи.

## Автоматизация (встроенные workflow)

- **Item added to project** → ставит `Todo`, чтобы новые задачи не висели без статуса;
- **Pull request merged** → `Done`;
- **Auto-add** по репозиторию → каждый созданный issue сам попадает на доску.

Движение `In Progress` и `In Review` делается вручную — перетаскивание карточки служит сигналом «я начал / я сдал».

## Правила

- Один PR = одна задача. В описании PR всегда `fixes #номер`;
- Разработчик не мержит сам — мердж только после аппрува CTO. Это гейт на закрытие задачи.
- Рекомендуется усилить через branch protection: требовать минимум один одобряющий ревью перед мерджем в основную ветку;
- Карточка в `In Review` без назначенного ревьюера — недоработка; ревьюер всегда CTO и другой разработчик.

## Сохраненные view

- **Для CTO** — фильтр `reviewer:@me is:open`: сразу видна очередь на ревью;
- **Для разработчиков** — группировка по `assignee:` каждый видит свои задачи.

## Контрольные точки CTO

1. **Ревью** — колонка `In Review`;
2. **Закрытие** — мердж под аппрувом CTO;
3. **Деплой** — отдельное решение после `Done`.
